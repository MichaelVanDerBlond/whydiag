# WhyDiag

WhyDiag — диагностическая система для Linux-серверов и прикладной инфраструктуры.

## Основные принципы

WhyDiag должен:

1. Получать данные из реальной системы.
2. Выполнять независимые диагностические проверки.
3. Не аварийно завершаться из-за ошибки одной проверки.
4. Различать нормальное состояние, предупреждение и ошибку.
5. Сохранять доказательства диагностического вывода.
6. По возможности указывать вероятную причину проблемы.
7. Коррелировать результаты разных проверок.
8. Формировать человекочитаемый отчёт.
9. Поддерживать машинно-читаемый формат результатов.
10. Оставаться расширяемым по мере добавления новых диагностических модулей.

## Архитектурные слои

### Inventory

Сбор фактической информации о системе.

Примеры:

- hostname
- OS information
- kernel
- uptime
- CPU
- memory
- swap
- filesystem
- timezone
- time synchronization

Inventory не должен самостоятельно принимать сложные диагностические решения.

### Checks

Checks анализируют данные Inventory или напрямую безопасно получают данные системы.

Каждая проверка должна возвращать структурированный Result.

Проверка должна быть независимой настолько, насколько это практически возможно.

### Core

Core отвечает за:

- регистрацию проверок;
- запуск;
- обработку ошибок;
- агрегирование результатов;
- итоговый статус;
- выполнение диагностического конвейера.

### Correlation

В дальнейшем WhyDiag должен поддерживать слой корреляции.

Он связывает несколько результатов.

Пример:

DNS: OK
TCP 443: OK
TLS: OK
Apache proxy: OK
Signaling service: ERROR

Вывод:

Вероятный источник проблемы Nextcloud Talk — signaling service.

### Reporting

Отчёты должны поддерживать как минимум:

- CLI text output;
- структурированное внутреннее представление.

В дальнейшем:

- JSON;
- HTML;
- machine-readable reports.

## Управление задачами и ревью

### Создание задачи

1. **Architect** создаёт новую задачу в файле `.ai/tasks/TASK-XXXX.md`.
2. **Developer** получает задачу и изучает её.

### Реализация задачи

1. **Developer** реализует задачу, изменяя существующий код или добавляя новые файлы.
2. **Developer** пишет тесты для проверки корректности реализации.
3. **Developer** обновляет документацию, связанную с задачей.

### Проверка и ревью

1. **Architect** выполняет review задачи в файле `.ai/reviews/TASK-XXXX.md`.
2. **Architect** оставляет замечания или одобрение.
3. **Developer** исправляет задачу по замечаниям Architect (если требуется).

### Принятие и отклонение изменений

1. Если изменения приняты, **Developer** сохраняет их в исходных файлах.
2. Если изменения отклонены, **Developer** вносит необходимые исправления и повторно отправляет на ревью.

## Версионирование и управление релизами

### Семантическое версионирование

Все изменения должны соответствовать семантическому версионированию:

- **MAJOR**: Несовместимые API изменения.
- **MINOR**: Совместимые функциональные улучшения.
- **PATCH**: Совместимые исправления ошибок.

### Обновление версии

1. **Developer** обновляет версию в файле `internal/version/version.go`.
2. **Architect** проверяет соответствие версии требованиям и одобрение.

## Тестируемость

Предпочтительная структура тестов:

- **Unit tests**: Для логики парсинга и принятия решений.
- **Integration tests**: Для проверки взаимодействия между компонентами.
- **End-to-end tests**: Для имитации реальных сценариев и валидации функциональности.

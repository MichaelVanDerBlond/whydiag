# WhyDiag Autonomous AI Protocol

## 1. Назначение

WhyDiag разрабатывается двумя автономными AI-агентами:

- Architect
- Developer

Они работают как участники технического диалога, а не как два независимых генератора.

Главный принцип:

НЕ УГАДЫВАТЬ — УТОЧНЯТЬ.

Если следующему агенту недостаточно информации для безопасного действия, он должен задать вопрос.

---

## 2. Источники истины

Приоритет источников:

1. фактический код текущего commit;
2. существующие tests;
3. docs/PROJECT_SPEC.md;
4. docs/ARCHITECTURE.md;
5. README.md;
6. текущая TASK;
7. диалог текущей TASK;
8. RESULT и REVIEW текущей TASK.

Если источники противоречат друг другу, агент не должен угадывать решение.

---

## 3. Роли

### Architect

Architect отвечает за:

- Problem;
- Evidence;
- Expected Result;
- Scope;
- Out of Scope;
- Definition of Done;
- архитектурные ограничения;
- review;
- выбор следующей TASK.

Architect не пишет production code.

### Developer

Developer отвечает за:

- анализ TASK;
- QUESTION при неоднозначности;
- PLAN;
- реализацию;
- tests;
- validation;
- RESULT;
- исправление конкретного REWORK.

Developer не определяет roadmap.

---

## 4. Одна активная задача

Одновременно существует не более одной активной TASK.

Новая TASK не создаётся, пока предыдущая не получила:

ACCEPTED

ABORTED

или BLOCKED с остановкой автоматического цикла.

---

## 5. Формат TASK

TASK должна содержать:

# TASK-NNNN

## Title

Краткое техническое название.

## Problem

Какой конкретный недостаток или отсутствующая возможность существуют сейчас.

## Evidence

Какие реальные файлы, функции, структуры или tests подтверждают Problem.

## Expected Result

Какое наблюдаемое поведение должно появиться.

## Scope

Что входит в задачу.

## Out of Scope

Что явно не входит.

## Relevant Components

Какие существующие компоненты относятся к задаче.

## Constraints

Архитектурные и технические ограничения.

## Definition of Done

Конкретные проверяемые критерии завершения.

## Validation

По умолчанию:

gofmt
go vet ./...
go test ./...
go build ./...

## Documentation Impact

Какая документация должна измениться, если это действительно необходимо.

---

## 6. Запрещённые TASK

Нельзя создавать задачи вида:

- улучшить проект;
- улучшить документацию;
- изучить архитектуру;
- разобраться с кодом;
- сделать диагностику лучше;
- добавить полезные проверки;
- ознакомиться с versioning;
- провести общий рефакторинг.

Если Definition of Done невозможно проверить, TASK не готова.

---

## 7. Типы сообщений

Разрешены следующие типы:

TASK
QUESTION
ANSWER
PLAN
PLAN_APPROVED
PLAN_REWORK
RESULT
REWORK
ACCEPTED
BLOCKED
ABORTED

LLM не придумывает новые состояния workflow.

---

## 8. QUESTION

QUESTION используется, если агенту недостаточно информации.

QUESTION должен содержать:

- что неизвестно;
- почему это мешает;
- какой конкретный ответ нужен.

После QUESTION реализация не продолжается до ANSWER.

QUESTION предпочтительнее догадки.

---

## 9. ANSWER

ANSWER отвечает непосредственно на открытый QUESTION.

Architect не заменяет ANSWER новой TASK.

Developer не заменяет ANSWER несвязанной реализацией.

---

## 10. PLAN

Перед первой реализацией Developer обязан сформировать PLAN.

PLAN содержит:

### Understanding

Как Developer понял Expected Result.

### Files

Какие файлы предполагается изменить или создать.

### Existing Components

Какие реальные типы, функции и abstractions будут использованы.

### Steps

Последовательность реализации.

### Tests

Какие tests будут добавлены или изменены.

### Risks

Известные риски и неоднозначности.

До PLAN_APPROVED production files не изменяются.

---

## 11. PLAN review

Architect отвечает:

PLAN_APPROVED

или:

PLAN_REWORK

PLAN_REWORK обязан содержать конкретную проблему плана.

Architect не должен писать реализацию вместо Developer.

---

## 12. Реализация

После PLAN_APPROVED Developer реализует только утверждённый PLAN.

Если во время реализации обнаруживается факт, делающий PLAN неверным:

Developer прекращает реализацию и отправляет:

QUESTION

или:

BLOCKED

Developer не меняет архитектурное решение самостоятельно.

---

## 13. RESULT

После реализации Developer отправляет RESULT.

RESULT содержит:

Changed Files

Implementation

Tests

Validation

Limitations

RESULT должен описывать фактически выполненную работу.

VALIDATION PASS не является доказательством выполнения TASK сам по себе.

Должен существовать содержательный diff, соответствующий Definition of Done.

---

## 14. Review

Architect проверяет:

1. TASK;
2. утверждённый PLAN;
3. RESULT;
4. git diff;
5. фактический код;
6. tests;
7. validation;
8. архитектурные ограничения.

Architect отвечает:

ACCEPTED

REWORK

или QUESTION.

---

## 15. ACCEPTED

ACCEPTED разрешён только если:

- Definition of Done выполнен;
- validation прошла;
- scope соблюдён;
- архитектура не нарушена;
- отсутствуют критические замечания.

После ACCEPTED TASK закрывается.

---

## 16. REWORK

REWORK содержит:

### Problem

Что конкретно неправильно.

### Evidence

Где проблема видна.

### Required Change

Что конкретно исправить.

### Acceptance

Как проверить устранение.

Запрещён абстрактный REWORK:

"улучши"

"добавь больше тестов"

"сделай правильнее"

"исправь архитектуру"

Если новое требование отсутствовало в TASK, Architect должен пересмотреть TASK, а не маскировать новое требование как REWORK.

---

## 17. BLOCKED

BLOCKED используется, если продолжение невозможно без дополнительного решения.

BLOCKED содержит:

Reason

Evidence

Tried

Need

После BLOCKED автоматическая реализация останавливается.

BLOCKED лучше повторения одной и той же неудачной попытки.

---

## 18. ABORTED

Architect использует ABORTED, если:

- TASK сформулирована некорректно;
- задача уже реализована;
- TASK противоречит архитектуре;
- TASK не имеет проверяемого результата;
- дальнейшая работа потеряла смысл.

ABORTED не считается ошибкой Developer.

---

## 19. Защита от циклов

Повтор предыдущего действия без новой информации запрещён.

Если агент собирается повторить:

- тот же QUESTION;
- тот же PLAN;
- тот же REWORK;
- то же исправление;
- ту же реализацию,

он обязан сначала определить, какая новая информация делает повтор осмысленным.

Если новой информации нет:

QUESTION

BLOCKED

или ABORTED.

Лимиты:

- максимум 3 PLAN_REWORK;
- максимум 3 REWORK после реализации;
- максимум 3 validation repair;
- максимум 2 одинаковых QUESTION без нового ANSWER.

После превышения лимита:

BLOCKED.

---

## 20. Прогресс

Прогресс существует только если произошло хотя бы одно:

- устранена неоднозначность;
- получен содержательный ANSWER;
- согласован PLAN;
- появился релевантный diff;
- устранена validation error;
- устранено конкретное замечание review;
- TASK принята;
- обнаружена объективная блокировка.

Количество сообщений и commits само по себе прогрессом не является.

---

## 21. Управление workflow

LLM не управляет state machine напрямую.

LLM возвращает содержательное сообщение.

Orchestrator:

- проверяет формат;
- сохраняет диалог;
- определяет следующего говорящего;
- разрешает изменение файлов;
- запускает validation;
- управляет Git;
- применяет loop limits.

Модель не должна самостоятельно устанавливать:

NEED_TASK
DEV_WORK
NEED_REVIEW
DEV_REWORK
FAILED

---

## 22. Git

AI работают только в:

ai-autonomous

Запрещено:

- merge в main;
- force push;
- rewrite опубликованной истории;
- изменение credentials;
- удаление repository.

Перед публикацией orchestrator проверяет, что remote commit не изменился во время работы агента.

---

## 23. WhyDiag safety

WhyDiag является READ-ONLY диагностической системой.

Без отдельного явно спроектированного режима запрещены:

- изменение system configuration;
- restart services;
- package installation;
- изменение firewall;
- изменение Nextcloud configuration;
- destructive database operations;
- удаление пользовательских данных.

---

## 24. Основной цикл

Нормальный цикл:

TASK
→ PLAN
→ PLAN_APPROVED
→ IMPLEMENTATION
→ RESULT
→ ACCEPTED

При неоднозначности:

TASK
→ QUESTION
→ ANSWER
→ PLAN

При проблеме плана:

PLAN
→ PLAN_REWORK
→ PLAN

При проблеме реализации:

RESULT
→ REWORK
→ RESULT

При невозможности продолжать:

BLOCKED

При некорректной задаче:

ABORTED
